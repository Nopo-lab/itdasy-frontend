## 4. 최우선 불일치 4개 실측 결과

### ✅ #1 비뷰티 이미지 — purpose 폴백 안 뜨고 422 (부분 확정, 분기 존재)
- **영수증(c20)** → `confidence=0.0` → **라우터 422** → FE는 `data.detail` 표시 = **"템플릿 내용을 인식하지 못했어요. 사진이 흐리거나 가격표/후기가 아닌 것 같아요."** (FE의 purpose 폴백 도달 못 함)
- **단, 홍보물(c12)** 처럼 shop_name/headline 등 내용이 있으면 → `has_content=true` → **200 purpose=promo** → FE 폴백 도달 = **"홍보물로 보여요. 지금은 가격표 사진만 카드로 만들 수 있어요."**
- **결론**: "가격표 아님"인데 **두 갈래 문구**가 존재 — 내용 0이면 422(흐림 탓하는 문구), 내용 있으면 200+폴백(용도 안내). 사용자 입장에서 "왜 어떤 건 흐리다 하고 어떤 건 홍보물이라 하나" 혼란.

### ✅ #2 422 문구 출처 — BE detail이 이김 (확정)
- FE 코드(151행): `_renderError(data.detail || '가격표를 인식하지 못했어요. 더 선명한 사진으로 다시 시도해 주세요.', true)`
- BE가 항상 detail 채움 → **FE 기본 문구는 영영 안 보임**. 실제 표시 = BE의 "템플릿 내용을 인식하지 못했어요…"
- 톤 불일치: FE는 "가격표/더 선명한 사진", BE는 "템플릿/가격표·후기" — 사용자에게 "템플릿"은 낯선 용어.

### ✅ #3 413 재현 — 가능하나 정상 경로선 사실상 도달 불가 (확정)
- 46MB 업로드 → **413 재현됨**(GFE HTML, 앱 도달 전 차단). FE는 `status===413` → "사진이 너무 커요. 6MB 이하로 줄여서 올려 주세요."
- **단**, FE가 업로드 전 `compressImageForUpload(1280, 0.85)`로 줄임 → 일반 사진은 6MB 미만으로 압축됨 → **413 거의 안 뜸**.
- **예외**: HEIC/HEIF는 압축 **스킵**(app-receipt-scan.js) → 원본이 6MB↑면 413 직격. 아이폰 기본 HEIC 사용자 위험. 문구 "직접 줄이세요"는 사용자가 손쓰기 어려움.

### ✅ #4 가격 누락 행 — 조용히 사라짐 (확정, BE+FE 이중 필터)
- c13: 5행("젤네일·헤드스파(문의)·두피케어(빈칸)·패디·연장(빈칸)") → **BE가 이미 2개만 반환**(name+price 둘 다 있어야 함, template_ocr.py:176). raw_text엔 5행 다 있음.
- FE `_normalizeServices`(29행)가 한 번 더 필터 → 카드 배지 **"시술 2개"**.
- **사용자는 3개 시술이 빠진 줄 모름.** "문의/상담가" 같은 한국 가격표 흔한 표기가 전멸.

## 7. 개선 우선순위

## 9. ⚠️ QA Harness payload 이슈 — OCR 400 아님 (별도 분류)

테스트 중 아래 400이 한 번 관측됨. **이건 staging OCR API의 검증 결과가 아니라, 요청 바디(JSON)를 만드는 하네스/툴 단계에서 깨진 것**이므로 OCR API 400 실패로 카운트하지 않는다.

```
API Error: 400 The request body is not valid JSON: no low surrogate in string: line 1 column 929169
```

### 판정 근거 (왜 OCR API 책임이 아닌가)
- `column 929169` = 한 줄(line 1)에 ~929KB가 인라인 → **큰 base64 이미지를 JSON 인라인으로 넣은 흔적**.
- `no low surrogate in string` = UTF-16 surrogate pair가 깨짐(high surrogate만 있고 low 없음) → 이모지/특수문자 혼입 또는 멀티바이트 절단으로 **요청 문자열 자체가 invalid JSON**.
- **이 OCR 엔드포인트(`/templates/extract-ocr`)는 `multipart/form-data` (필드명 `file`) 전용**이라 JSON 인라인 바디를 애초에 받지 않는다 → "request body is not valid JSON"은 staging FastAPI가 낸 메시지 형식도 아님(이 API의 검증 실패는 항상 `{"detail":..., "request_id":...}` 구조, 아래 표 참조).
- 즉 이 400은 **OCR API에 도달하기 전, payload 직렬화 레이어에서 발생**. → **분류: QA Harness / curl payload issue.**

### 올바른 재시도 결과 (동일 이미지, form-data)
| 호출 | 방식 | HTTP | 결과 |
|---|---|---|---|
| 01_clear_table.jpg 재시도 | `curl -F "file=@...;type=image/jpeg"` (인라인 JSON 금지) | **200** | `purpose=price/nail`, services 정상 파싱 → **OCR API 정상, 400은 하네스 탓 확정** |

### 진짜 400/422는 의도적으로 따로 재현 (깨진 JSON 아님)
| 재현 | 방법 | 실측 HTTP | 응답(detail) | request_id |
|---|---|---|---|---|
| A 필수 필드 누락 | multipart인데 `file` 없음 | **422** | `요청 형식이 올바르지 않습니다.` / `body.file: Field required` | 2e75f8be |
| B 잘못된 content-type | `application/json` 바디를 multipart 엔드포인트에 | **422** | 동일(`body.file: Field required`) | 1114473f |
| C 손상 이미지 바이트 | 유효 multipart + 깨진 JPG | **400** | `이미지를 처리할 수 없어요. 다른 사진으로 시도해 주세요.` | 2b097194 |
| D 잘린 JPG | 유효 multipart + truncated JPG | **400** | 동일 | 844c5d05 |

**결론**:
- 이 API의 **요청 형식 오류(필드 누락·content-type 오류)는 400이 아니라 422**(구조화된 `errors[]` + `request_id`)로 응답한다.
- **진짜 400**은 "유효한 multipart지만 이미지 바이트가 손상"일 때만 발생(C·D). 섹션 3의 c30/c31 400은 이 정상 경로로 재확인됨.
- 보고서의 OCR 400 카운트(섹션 2 "에러 핸들링 400…정상")는 **C·D(손상 이미지)만 해당**하며, surrogate 400과 무관하다.
